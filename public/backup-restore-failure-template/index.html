Backup & Restore Failure Template

A failed backup is a silent continuity risk; a failed restore is an emergency. Walk these five checks to confirm your last good recovery point, isolate agent or repository faults, and verify a clean test restore.

THE TEMPLATE

Five checks to protect recoverability.

The worked example below is illustrative — not a real incident. It shows how each section reads when filled in.

SECTION 01

Confirm the last known good recovery point

Before restarting failed jobs, record the exact timestamp of the last verified good backup (on-site and off-site/immutable) so leadership knows current RPO exposure.

ILLUSTRATIVE EXAMPLENightly ERP database backup failed at 02:14 UTC; previous verified restore point is 26 hours old on local NAS and immutable S3 bucket. Not a real incident.
SECTION 02

Check repository capacity, retention, and immutability

Verify free disk space on the backup target, object-storage quota, and whether retention/immutability locks prevented old chains from pruning.

ILLUSTRATIVE EXAMPLEBackup repository volume hit full capacity after a one-time 400 GB file migration triggered an oversized incremental chain. Not a real incident.
SECTION 03

Inspect source snapshot, VSS, or agent errors

Check Windows VSS writers, hypervisor snapshot consolidation, database log-truncation errors, and service-account credential or certificate expirations.

ILLUSTRATIVE EXAMPLESQL VSS writer entered Failed state due to expired service account password rotated during monthly patching. Not a real incident.
SECTION 04

Check network path, throttling, and encryption keys

Confirm the backup proxy can reach the repository without packet loss or firewall blocks, and verify that encryption passphrases or KMS keys are accessible for restore.

ILLUSTRATIVE EXAMPLEFirewall rule update blocked TCP 443 from backup proxy subnet to off-site object storage endpoint. Not a real incident.
SECTION 05

Run a clean test restore to prove recovery

Do not close the incident on a green backup icon alone. Restore a sample file, database, or VM to an isolated sandbox and record the verification output.

ILLUSTRATIVE EXAMPLERestored ERP database to isolated staging instance, ran integrity check with zero errors, and documented updated RPO compliance. Not a real incident.

QUESTIONS

Backup and restore failures, answered briefly.

What should you confirm first when a backup job fails?

Confirm the timestamp and integrity of the last known good recovery point first so you know your current RPO exposure before changing job settings or retargeting repositories.

Why do backups succeed while restores still fail?

Common causes include corrupt incremental chains, missing encryption keys, changed permissions on the restore target, or application-inconsistent snapshots. Only a verified test restore proves recoverability.

Is the worked example a real incident?

No. The example on this page is illustrative — not a real incident from SolveStack or any customer.
