Root Cause Analysis Tools

Root cause analysis tools do not share one job. The 5 Whys follows a single chain. A fishbone diagram sorts candidate causes into categories. A Pareto chart ranks recurring categories by a count. FMEA looks forward, at how a design or a process could fail. A fault tree shows which combinations of faults are enough to cause one defined event. A tool produces candidates or a ranking. It does not prove the cause. Proof is a later check: the effect stays gone after you remove or control that cause. SolveStack publishes a worksheet where one exists, and says so where it does not.

01

CHOOSE

Match the tool to the evidence you already have.

Start from the effect, not from a favorite diagram. If the method needs a kind of evidence you do not have, pick a different method or go collect that evidence. Stopping at human error, or at the component that broke, names a place. Ask what in the system allowed that action or that failure, and write the evidence for the answer.

STEP 01

Name the effect

Write what was observed, when, including the timezone, and the extent, with the measurements you actually have. Adjectives are not a problem statement. If other people need that record while the incident is still open, put it on the incident report template. The report is the account of what happened. The analysis is the account of why.

STEP 02

Separate one case from a recurring set

A Pareto chart needs categories you can count in one unit, across many events. One incident is not a distribution. Skip the chart and study the case in front of you. If the same category keeps returning, the chart is how you choose which category to investigate first, and it still does not explain why that category happens.

STEP 03

See whether one chain is already visible

Several kinds of cause still plausible: draw a fishbone and pick one branch to test. One chain you can already follow: use the 5 Whys, and put evidence beside each answer. Two causes that do not depend on each other are two chains. Forcing them into one list hides one of them.

STEP 04

Ask whether faults have to combine

If the event happens only when several faults are true together, or if any one of several faults is enough, a fault tree makes that logic visible. If one fault was enough and the evidence shows it, you do not need the tree. An OR gate means any one input is enough. An AND gate means every listed input is required.

STEP 05

Keep the forward look separate

The investigation explains the failure you had. FMEA asks how a design or a process step could fail, including failures you did not just watch. Do the investigation first. Use an FMEA when you change the design so the same mode is harder to repeat. Do not file the FMEA as the incident write-up. SolveStack does not publish an FMEA page.

STEP 06

File the record, then the actions

The timeline, the chain, the contributing factors, and the check that the fix held go on the root cause analysis template. Owners, dates, and the effectiveness check go on the corrective action plan template. A diagram with no record, and a record with no checked action, are both unfinished.

5 WHYS

One chain, with evidence on every step

The 5 Whys is the questioning chain used in the Toyota Production System. You state the effect, ask why it happened, and let that answer become the next question. Five is a usual length, not a rule: stop when you reach a cause the team can change, and stop earlier if the next answer would be a guess. Write the evidence beside each why. A step with no evidence is a hypothesis, and the chain stays a hypothesis until the corrective action is checked. The worksheet is the 5 whys template.

FISHBONE

Categories first, then one branch to test

A fishbone diagram, also called an Ishikawa diagram or a cause-and-effect diagram, puts one effect at the head and hangs possible causes on category bones. The usual manufacturing set is the 6Ms: Methods, Machines, Materials, Manpower (People), Measurement, and Mother Nature (Environment). Service work often uses the 4Ps, Policies, Procedures, People, and Plant/Technology, or the 4Ss, Surroundings, Suppliers, Systems, and Skills. The people bone is for skills, staffing, and handoffs. A colleague's name is not a cause. An empty category is a prompt to look again, not an order to invent a cause. The chart does not say which branch is true. Test one branch, and leave the others on the chart so they are not forgotten. The fishbone diagram template includes the category sets and a blank CSV.

PARETO

A ranking of categories, not a cause

A Pareto chart is a bar chart of categories in descending order, often with a line for the cumulative share. In quality work this ranking is called a Pareto analysis: look at the few categories that account for most of the total you chose to count. The count has to be one unit. Mixing incidents, minutes, and cost on one axis makes the order meaningless. A handful of events can change the order when the next week arrives. If adding or removing a few events would change which category is first, treat the chart as a hint and look at the next category too. People sometimes quote the Pareto principle as 80/20. That ratio is an illustration, not a result you should expect. Read the share off your own counts. SolveStack does not publish a Pareto template.

FMEA

How it could fail, before it does

Failure mode and effects analysis, set out for equipment in the 1949 US military procedure MIL-P-1629, walks a design or a process step and asks how that piece can fail, what the effect is, and how bad the effect is. A design FMEA looks at the design. A process FMEA looks at the steps that build or run it. Worksheets often score severity, occurrence, and detection on a short scale. Multiplying those scores produces a risk priority number on sheets that still use one. That product is a sort key, not a probability, and a higher product is not automatically the mode to work on first when another mode is more severe. The 2019 AIAG-VDA FMEA Handbook ranks the need for action with an Action Priority of high, medium, or low, so severity is not washed out by the multiplication. FMEA is the wrong write-up for an incident you just had. SolveStack does not publish an FMEA worksheet or an FMEA page.

FAULT TREE

Which combinations are enough

Fault tree analysis was developed at Bell Laboratories in 1962 for the Minuteman program. You name one undesired top event, then show the faults that can cause it. An OR gate means any one input is enough. An AND gate means every input is required. Other gates exist. IEC 61025 is the international standard that describes the method. Qualitative analysis is the shape of the tree: it is useful without failure rates. Quantitative analysis needs rates you actually have. Do not invent a rate to make the arithmetic work. Basic events are the faults where you stop decomposing, because you can observe them or because that is the level you will change. If you cannot yet draw the system, you are not ready for the tree. There is no fault tree template on this site. The top event and the evidence belong on the root cause analysis template.

OTHERS

Change, barriers, and a long timeline

Change analysis compares the failing case with a working one along what, where, when, and extent: an is / is not list. The differences are places to investigate, not yet causes. Use it when something that worked has started to fail and you can name a comparison that still works. Barrier analysis lists the controls that should have stopped the outcome, such as an alarm, an approval, a test, or a permission, and marks which were missing, weak, or bypassed. A control you wish had existed is a recommendation, not a finding that it failed. Events and causal factors charting, used in some energy-industry investigations, draws the timeline and hangs the conditions that shaped each event on that line. It earns its keep when the story is long. A short single chain does not need it. Eight Disciplines (8D) and DMAIC are sequences for when to contain, when to analyze, and when to check. They are not cause-finding tools. Inside them, a team still uses a chart, a chain, or a tree from this page.

05

QUESTIONS

Tools, answered briefly.

What are root cause analysis tools?

Root cause analysis tools are methods for moving from an effect to a cause you can change. A tool sorts evidence or candidates. It does not, by itself, prove the cause. Proof is a later check that the effect stays gone after that cause is removed or controlled. This page covers the 5 Whys, the fishbone diagram, the Pareto chart, FMEA, fault tree analysis, change analysis, barrier analysis, and events and causal factors charting, and it links to a SolveStack template where one exists.

When should I use the 5 Whys?

Use the 5 Whys when you have one effect and a chain you can follow, and you can write evidence beside each answer. Five is the usual length, not a quota. Stop on a cause the team can change. If a second cause does not depend on the first, start a second chain. The 5 whys template is the worksheet for that chain.

When should I use a fishbone diagram?

Use a fishbone diagram when several kinds of cause are still plausible and you need them on one chart before you choose a branch to test. The finished chart is a sorted list of candidates, not a finding. Manufacturing work often uses the 6M categories. Service work often uses the 4Ps or the 4Ss. The fishbone diagram template has those sets, a worksheet, and a blank CSV.

When is a Pareto chart the right tool?

Use a Pareto chart when the same kinds of event keep recurring and you can count them in one unit, such as occurrences or minutes of impact. The chart ranks categories so you can see which ones account for most of the total. Do not use it for a single incident. Do not expect a fixed split such as 80/20. The share is whatever your counts show. SolveStack does not publish a Pareto template. After the chart selects a category, continue with the 5 whys or the root cause analysis template.

How do FMEA and fault tree analysis differ?

FMEA starts from a design or a process step and asks how that piece can fail and what the effect would be. It is usually done before the failure, or when you are about to change the design. Fault tree analysis starts from an undesired top event and uses logic gates to show which combinations of faults are enough to cause it. An OR gate means any one input is enough. An AND gate means every input is required. SolveStack does not publish an FMEA page or a fault tree template.

Which of these tools have a SolveStack template?

SolveStack publishes a 5 whys template, a fishbone diagram template, a root cause analysis template for the full record, an incident report template, and a corrective action plan template for the actions after a confirmed cause. Pareto charts, FMEA worksheets, and fault trees are explained on this page and are not separate pages.
