THE TEMPLATE

Five checks, in the order that isolates the fault.

The worked example below is illustrative — not a real incident. It shows how each section reads when filled in.

SECTION 01

Confirm the scope

Before touching the gateway, establish the blast radius: one user, one site, one client version, or everyone. Scope decides where you look — a single user is an account or client problem; everyone at once is gateway, ISP, or identity. Record the first report time and the last known good connection.

ILLUSTRATIVE EXAMPLEAll remote staff (about 140 users) lost VPN at 08:10 CT; office LAN unaffected; first report 08:12 via the help desk. Last known good: 07:55 successful connections in the gateway log. Not a real incident.
SECTION 02

Gateway and the last change

Check the concentrator or cloud gateway the way you would any suspect service: is it up, is it passing any traffic, and what changed in the last 24 hours? Firmware pushes, certificate renewals, and ISP maintenance line up with outage start times more often than hardware dies quietly.

ILLUSTRATIVE EXAMPLEGateway CPU and sessions normal; no firmware change in 14 days. The ISP status page showed a regional routing event starting 08:05. Not a real incident.
SECTION 03

Test the authentication path

Most 'VPN is down' reports are identity failures in disguise: an IdP outage, an expired RADIUS or SAML certificate, or an MFA policy change. Connect with a known-good test account. If the tunnel establishes but sign-in fails, the network is fine — stop rebooting it.

ILLUSTRATIVE EXAMPLEA test account reached the gateway and received an MFA prompt; the IdP status page showed degraded authentication from 08:02. The root cause is upstream of the VPN. Not a real incident.
SECTION 04

Rule out client spread

If only some users fail, compare what the failing clients share: OS version, VPN client build, a recent agent update. A client pushed at 07:00 that breaks split tunneling looks identical to an outage from the help desk's chair.

ILLUSTRATIVE EXAMPLEFailing users were all on client 7.4.1, pushed that morning; 7.3.x users connected normally. Rolling back the client update cleared the reports. Not a real incident.
SECTION 05

Capture evidence before escalating

Vendors and ISPs close vague tickets. Escalate with the scope statement, the gateway log excerpt around the first failure, the auth-path test result, and the exact timestamps. That bundle turns a three-day ticket into a same-day answer.

ILLUSTRATIVE EXAMPLEEscalation packet: scope statement, gateway log 08:00–08:20, test-account result, ISP event ID. The vendor acknowledged an upstream fault within the hour. Not a real incident.

QUESTIONS

VPN outages, answered briefly.

What should a VPN outage checklist include?

Scope first (who cannot connect, since when), then the gateway and its recent changes, a test of the authentication path with a known-good account, a client-version comparison, and an evidence bundle for escalation. This checklist walks those five in order, because each answer rules a whole layer in or out.

How do I tell whether a VPN outage is the gateway or authentication?

Connect with a known-good test account and watch where it fails. If the tunnel never establishes, look at the gateway, the ISP, or the client. If the tunnel establishes but sign-in or MFA fails, the network path is fine and the fault is in the identity layer — an IdP outage, an expired certificate, or a policy change.

Why does scope matter so much in a VPN outage?

Because scope is the diagnosis shortcut. One user failing is an account or client problem; one site failing points at that site's circuit or gateway peer; every remote user failing at the same minute points at the gateway, the ISP, or the identity provider. Establishing scope takes minutes and prevents hours of checking the wrong layer.
