FIELD GUIDE / INCIDENT REPORT

WHAT HAPPENED → WHO OWNS THE NEXT CHANGE

IT Incident Report Template

An incident report template is the record of what happened, written for someone who was not in the room. It holds a summary, a timeline, the impact, the root cause as far as it is known, and the corrective actions with an owner on each line. Copy the blank report, or read the invented example. The cause chain belongs on the 5 whys template. The tracked actions belong on the corrective action plan template.

01

WHAT IT IS FOR

A record of the incident, not the whole analysis.

Write the report so a later reader can see what failed, what was done, and who owns what remains. The report points at the analysis. It does not repeat every why. If one chain is the wrong shape, the root cause analysis tools page is how you choose another method. The root cause analysis template is the full record when this report is not enough. Use a role for every owner. A personal name is not a substitute for the role.

Six fields. The report is done when each one is filled or marked not confirmed.
Field What to write
Summary What failed, where, the window with a timezone, how it was detected, and the role that owns the report.
Timeline Timestamped observations and actions, including the dead ends. A later time should not have to be reconstructed from memory.
Impact What was affected, and what was not, in the terms you actually have. Leave a measurement out when you do not have it.
Root cause A cause the team can change, or the words "not confirmed", plus the method and where the chain is filed.
Corrective actions The changes that follow the cause. Each line has an owner role, a due date, and a status.
Owners The report owner, the incident lead, and the owner of every action. A crowd is not an owner.
FIELD 01

Summary

An incident ID, what failed, where, the window with a timezone, how it was detected, and the role that owns the report. Someone reading this later should be able to find the timeline and the analysis from this block alone.

ILLUSTRATIVE EXAMPLEINC-2026-044. CI jobs against the internal package registry returned HTTP 401 from 09:40 to 10:06 UTC on 2026-10-08. Detected by the CI failure alert. Report owner: platform lead. Not a real incident.
FIELD 02

Timeline

One line per observation or action, with the time and the timezone. Include the step that did not help. The timeline is the evidence the summary stands on. If you cannot write it down during the incident, say which parts were reconstructed afterward.

ILLUSTRATIVE EXAMPLE09:40 UTC, jobs start returning HTTP 401 and the auth log shows expired-token errors for the CI robot credential. 10:06 UTC, platform on-call reissued that credential, revoked the expired one, and the failed jobs were re-run. Not a real incident.
FIELD 03

Impact

State what was affected and what was not. Use a measurement only when you have it, and name the source. An impact section with a gap is more useful than a section filled in from memory.

ILLUSTRATIVE EXAMPLEMerge builds failed during the window. No production runtime was affected. Source: the CI failure alert and the teams on the call. Not a real incident.
FIELD 04

Root cause

State the cause as something the team can change, or write "not confirmed". Name the method. Point at the chain instead of pasting every why. The 5 whys template is that chain. If the cause is not confirmed yet, do not write a permanent fix in the next field.

ILLUSTRATIVE EXAMPLEMethod: 5 Whys. The migration checklist covered human accounts and omitted service credentials, so the robot credential expired with no renewal job. Contributing factor, not the cause: the alert watched job failure, not upcoming expiry. Not a real incident.
FIELD 05

Corrective actions

One line each: the change, the owner role, the due date, and the status. The change should be a system, a procedure, or a control. The corrective action plan template is where those lines are tracked until an effectiveness check is written down. This report lists them so the incident points at the plan.

ILLUSTRATIVE EXAMPLEReissue and revoke the CI robot credential (platform on-call, done the same day). Add service credentials to the rotation checklist and add a renewal job (identity engineering). Inventory other robot credentials with no renewal job (identity engineering). Not a real incident.
FIELD 06

Owners

Name the role that owns the report, the role that led the incident, and the role on every action. An owner is a role that can change the system. A crowd is not an owner. If a role is not yet named, write "unassigned" rather than leaving the line blank.

ILLUSTRATIVE EXAMPLEReport owner: platform lead. Incident lead: platform on-call. Action owners: platform on-call and identity engineering. Not a real incident.

INCIDENT REPORT — WORKED EXAMPLE
Not a real incident.
=================================
Incident ID: INC-2026-044
Date: 2026-10-08, 09:40-10:06 UTC
Report owner (role): platform lead
Status: closed

1. SUMMARY
   CI jobs against the internal package registry returned HTTP 401.
   Detection: the CI failure alert.
   Systems: internal package registry, CI robot credential.

2. TIMELINE
   09:40 UTC — jobs start returning HTTP 401.
   09:40 UTC — auth log shows expired-token errors for the CI robot credential.
   10:06 UTC — platform on-call reissued the credential, revoked the expired one, and the failed jobs were re-run.
   10:06 UTC — current impact stopped.

3. IMPACT
   Merge builds failed during the window.
   No production runtime was affected.
   Source: the CI failure alert and the teams on the call.

4. ROOT CAUSE
   Confirmed cause: the registry migration checklist covered human accounts and omitted service credentials, so this robot credential expired with no renewal job.
   Method: 5 Whys.
   Evidence: auth log expired-token errors from 09:40 UTC; secret metadata showing expiry that morning; checklist in the infrastructure repo with no service-credential row.
   Contributing factor: the alert watched job failure, not upcoming expiry. It delayed detection. It did not cause the expiry.
   Analysis: 5 whys for INC-2026-044, filed with the root cause analysis.

5. CORRECTIVE ACTIONS
   - [x] Reissue and revoke the CI robot credential, then re-run the failed jobs — platform on-call — 2026-10-08 — done
   - [x] Add service credentials to the rotation checklist, and add a renewal job that pages if it fails — identity engineering — 2026-10-22 — done
   - [x] Inventory other robot credentials with no renewal job, and name a role for each one that remains — identity engineering — 2026-11-05 — done
   Plan: corrective action plan CAP-2026-044, including the effectiveness check.

6. OWNERS
   Report owner (role): platform lead
   Incident lead (role): platform on-call
   Action owners (roles): platform on-call, identity engineering

RUN IT LOCALLY

Write the report while the incident is open.

The timeline is only as good as the notes taken during the incident. Open the incident-report mode, keep the summary next to the evidence, and export the record when it should leave the browser.

Open SolveStackSee export formats
  1. The original symptom — the sentence the summary is built from
  2. Commands and observations — the raw material of the timeline
  3. Evidence — logs and diffs named in the impact and the cause
  4. Competing hypotheses — written down before you commit to one
  5. Causes ruled out — the dead ends, kept on the timeline
  6. The confirmed root cause — or an explicit "not confirmed"
  7. The validation — what showed the current impact had stopped
03

QUESTIONS

Incident reports, answered briefly.

What is an incident report template?

An incident report template is a form for the record of an incident: a summary, a timeline, the impact, the root cause as far as it is known, and the corrective actions with an owner on each one. The report tells a later reader what happened. It does not replace the analysis or the action plan.

What is an incident report for?

An incident report is the account other people can read without having been in the room. It fixes the summary, the timeline, and the impact while they are still known, and it points at the cause and the actions. Write it during the incident. Do the deeper analysis after the current impact has stopped.

What fields should an incident report include?

Include a summary, a timestamped timeline, the impact, the root cause or an explicit note that it is not confirmed, the corrective actions, and an owner for the report and for each action. Use a role for each owner. A personal name is not a substitute for the role.

How is an incident report different from a root cause analysis?

The incident report records what happened. A root cause analysis explains why, and keeps the cause chain, the contributing factors, and the check that the fix held. If the cause is still a guess, say so in the report and continue on the root cause analysis template. The 5 whys template is the short chain. The corrective action plan template is where owners, dates, and the effectiveness check are tracked.

Where do corrective actions and owners belong?

Each corrective action on the report names the change, the owner role, and a due date. The report lists them so the incident has a record. The corrective action plan template is where those lines are tracked until an effectiveness check is written down. An action with no owner and no due date is not assigned.

Can I use this incident report template offline?

Yes. Copy the plain-text report into any document, or print this page. Nothing typed into this page is saved or sent anywhere. The SolveStack app linked from this page stores an investigation in your browser and can export Markdown, HTML, JSON, and ZIP. It has no account and no cloud service.
