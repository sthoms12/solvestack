THE TEMPLATE

Five checks, from the error to the renewal.

The worked example below is illustrative — not a real incident. It shows how each section reads when filled in.

SECTION 01

Record the exact error

Browsers and clients report different errors for different faults — expired, name mismatch, untrusted chain, revoked. Capture the verbatim error and the client that showed it. The wording alone eliminates half the suspects before you inspect anything.

ILLUSTRATIVE EXAMPLE'Certificate expired' in Chrome for the customer portal, recorded 07:58 CT with a screenshot; the API client reported a generic TLS failure for the same endpoint. Not a real incident.
SECTION 02

Inspect the served chain

Ask the server what it actually serves: leaf subject, issuer, validity dates, SANs, and whether the intermediate chain is complete. The certificate in your vault may be renewed while the server still presents the old one — trust the wire, not the inventory.

ILLUSTRATIVE EXAMPLEThe served leaf expired 6 days earlier despite a renewed certificate sitting in the vault; intermediates complete. The renewal was never installed on this node. Not a real incident.
SECTION 03

The wrong-binding trap

Multi-site servers and load balancers bind certificates per site or per node. A renewal installed on the wrong binding — or on three of four pool members — produces an outage that 'should be fixed' and intermittently is. Check every endpoint that answers for the name.

ILLUSTRATIVE EXAMPLETwo of four load-balanced nodes still served the expired leaf; health checks passed because TLS was not part of the probe. A rolling restart after install cleared the errors. Not a real incident.
SECTION 04

Client-side trust and clocks

If only some clients fail, suspect the clients: a device clock set wrong makes valid certificates look expired, and an outdated trust store rejects modern chains. Reproduce from a known-good client on the same network before touching the server again.

ILLUSTRATIVE EXAMPLEThe remaining reports traced to a kiosk fleet whose clocks drifted after a time-service failure — the certificates were valid; the kiosks' dates were not. Not a real incident.
SECTION 05

Assign the renewal — and the next one

Close the loop while it hurts: record the renewal owner, the new expiry date, and where the certificate is bound. The postmortem that matters for certificates is a calendar entry 30 days before the next expiry, owned by a person, not a team alias.

ILLUSTRATIVE EXAMPLERenewal owner assigned; the expiry added to the team calendar with a 30-day alert; the other three certificates on the same host inventoried with dates. Not a real incident.

QUESTIONS

Certificate failures, answered briefly.

What should I check first when a certificate expired error appears?

Record the exact error and client, then inspect the certificate the server actually serves — its dates, issuer, and chain. The renewed certificate may exist in a vault while the server still presents the old one, or the renewal may be bound to the wrong site. Trust what is on the wire.

Why do only some users see a certificate error?

Three usual reasons: a load-balanced pool where only some nodes serve the bad certificate, a client whose clock is wrong so valid certificates look expired, or an outdated client trust store that rejects the chain. Compare a failing and a working client against the same endpoint to separate server faults from client faults.

How do I see the certificate a server is really serving?

Connect to the endpoint and read the presented chain — browsers show it behind the padlock's certificate details, and command-line TLS tools print the leaf and intermediates with dates and issuers. Check every address the name resolves to, not just the first.
