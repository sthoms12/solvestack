5 Whys Template

01

THE SESSION

How a 5 Whys session works.

The 5 Whys is the questioning chain used in the Toyota Production System. IT incident reviews use the same move. One session follows one path. Write the evidence beside every answer, or the chain is a hypothesis. The root cause analysis tools page is where this method sits next to fishbone, Pareto, FMEA, and a fault tree.

STEP 01

Start from one observation

Write the problem as something observed: an error, a failed job, a path that stopped working. Include when, with the timezone, and the extent, in the terms you actually have. Do not start from the cause you already suspect. If other people need that account while the incident is still open, put it on the incident report template.

STEP 02

Ask why, and name the evidence

The answer should point at a log line, a config value, a timeline entry, or a change record. If you cannot point at anything, mark the step unverified. That answer is the next question. A step with no evidence does not become true because the meeting agreed with it.

STEP 03

Stop on a cause the team can change

Stop when another why would only restate the cause, and the team can change that cause. Do not stop on a personal name if a system condition still explains how the mistake was possible. Five steps is a teaching convention, not proof that the fifth answer is the cause. Stop earlier when the next answer would be a guess.

STEP 04

Split a second independent cause

One chain follows one path. If a second cause does not depend on the first, start a second chain on this worksheet. Forcing them into a single list hides one of them. Owners, due dates, and the check that the action worked belong on the corrective action plan template, not as extra whys.

5 WHYS — WORKED EXAMPLE
Not a real incident.
=======================
Problem: CI jobs against the internal package registry returned HTTP 401.
Window: 2026-10-08, 09:40-10:06 UTC.
Extent: merge builds failed. No production runtime was affected.
Incident report: INC-2026-044

1. Why did the jobs fail?
   Answer: The registry rejected the CI robot credential.
   Evidence: auth log shows expired-token errors from 09:40 UTC.

2. Why was the credential rejected?
   Answer: The credential expired that morning.
   Evidence: secret metadata shows the expiry that morning.

3. Why did it expire with no replacement in place?
   Answer: No renewal job existed for that credential.
   Evidence: the credential has a fixed expiry and no renewal job.

4. Why was there no renewal job?
   Answer: The migration checklist covered human accounts and omitted service credentials.
   Evidence: checklist in the infrastructure repo, with no service-credential row.

5. Why did that omission survive the migration?
   Answer: The checklist was the control the migration used, and it had no line for service credentials. That is a cause the team can change, so the chain stops.
   Evidence: the checklist itself.

Contributing factor (not another why): the alert watched job failure, not upcoming expiry. Record it on the root cause analysis. It delayed detection. It did not cause the expiry.
Corrective actions: corrective action plan CAP-2026-044.
Switch to a deeper RCA if a second independent cause shows up, or if this chain is still unchecked.

03

WHEN TO SWITCH

When to switch to a deeper RCA.

Stay with the 5 Whys while one chain, with evidence on each step, still explains the effect. Switch to a deeper root cause analysis when the worksheet would have to hold a timeline, a second independent cause, contributing factors, or a check that the fix held. The chain can move into the root cause analysis template as one section. It does not have to be thrown away.

Stay on this worksheet, or move the work to the record that can hold it.
What you have Stay with the 5 Whys Switch
One effect, one chain, evidence on each answer Finish the chain. Stop on a cause the team can change. No switch yet. File the chain when the record needs a home.
A second cause that does not depend on the first Start a second chain on this worksheet. Also file both chains on the root cause analysis template.
A timeline, contributing factors, or a check that the fix held Keep the chain as one section of the larger record. Root cause analysis template.
Several kinds of cause still open, or faults that must combine Do not force them into one list of whys. Root cause analysis tools, then the method that fits.
Owners, due dates, and an effectiveness check Name the action in one line. Corrective action plan template.
An account for people who were not in the room Point at this chain. Do not retell it. Incident report template.

05

QUESTIONS

5 whys, answered briefly.

What is a 5 whys template?

A 5 whys template is a worksheet for one cause chain. You state what you observed, ask why it happened, and let each answer become the next question. Each step names the evidence. Five is the usual length, not a quota. Stop on a cause the team can change.

How does a 5 whys session work?

Start from one observation. Ask why, and write the evidence beside the answer. That answer is the next question. Stop when the cause is something the team can change, or when the next answer would be a guess. If a second cause does not depend on the first, start a second chain. A step with no evidence stays a hypothesis.

When should I switch from the 5 whys to a deeper root cause analysis?

Switch when the incident needs more than one chain, when you still have to record the timeline and the contributing factors, or when the chain is a hypothesis you have not checked. The root cause analysis template is that fuller record. If several kinds of cause are still open, or faults have to combine, use the root cause analysis tools page to pick a different method. The 5 whys chain can still be one section of the larger record.

What belongs on the corrective action plan instead?

The 5 whys worksheet can name the action that follows the cause. Owners, due dates, and the check that the action worked belong on the corrective action plan template. The incident report template is the account of what happened, and it can point at this chain instead of repeating it.

Is the worked example a real incident?

No. The package-registry example on this page is invented so the chain can be read from the effect to a cause the team can change. It is not a record from a real outage. Not a real incident. The same fictional case is used on the corrective action plan template.

Can I use this 5 whys template offline?

Yes. Copy the plain-text worksheet into any document, or print this page. Nothing typed into this page is saved or sent anywhere. The SolveStack app linked from this page stores an investigation in your browser and can export Markdown, HTML, JSON, and ZIP. It has no account and no cloud service.
