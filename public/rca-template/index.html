THE TEMPLATE

Six sections. No fluff.

SECTION 01

Problem statement

One paragraph: what happened, what was affected, and when it was detected. Write it so someone who was not on call can understand the incident in thirty seconds. Include the blast radius — users, systems, revenue — with numbers, not adjectives.

ILLUSTRATIVE EXAMPLEPayment API returned HTTP 500 for ~12% of checkout requests, 14:02–14:47 UTC. 340 failed orders. Detected by checkout-error alert, not by a customer report.
SECTION 02

Incident timeline

A timestamped sequence from first symptom to confirmed resolution. Record what was observed and what was done at each step — including the dead ends. The timeline is the evidence the rest of the analysis stands on; an RCA without one is a guess.

ILLUSTRATIVE EXAMPLE14:02 — alert fires. 14:09 — on-call confirms 500s on /pay/confirm. 14:18 — database primary disk at 100% found. 14:31 — disk expanded, errors stop. 14:47 — error rate back to baseline, incident closed.
SECTION 03

The 5 whys

Ask "why" repeatedly — typically five times — with each answer becoming the next question. This is what moves the analysis past the surface symptom to the cause you can actually fix. Write each why down; the chain is the deliverable, not just the final answer.

ILLUSTRATIVE EXAMPLEWhy did checkout fail? The database rejected writes. Why? Its disk was full. Why? Log retention had no cap. Why? The retention policy was never configured after the migration. Why? Migration runbook had no storage-verification step.
SECTION 04

Contributing factors

Causes that made the incident worse or more likely, but are not the root cause. Keep this list separate from the root cause — mixing them is the most common RCA failure. Contributing factors still deserve action, just not the headline.

ILLUSTRATIVE EXAMPLEAlert threshold was set at 95% disk, leaving ~9 minutes of headroom. Staging environment has 10× the disk headroom of production, so load tests never caught it. The runbook's rollback step assumed a healthy database.
SECTION 05

Corrective actions

Every action gets an owner and a date — an action without both is a wish. Separate immediate fixes (stop the bleeding) from systemic fixes (stop the recurrence). If an action cannot be scheduled, say so explicitly rather than letting it drift.

ILLUSTRATIVE EXAMPLEImmediate: cap log retention at 30 days (Priya, this week). Systemic: add storage-verification step to the migration runbook (Marcus, next sprint). Systemic: disk-usage alert at 80% with paging at 90% (Priya, next sprint).
SECTION 06

Follow-ups

Close the loop: did the corrective actions actually happen, and did they work? Record the validation — the test, metric, or review that proved the fix. An RCA whose actions were never verified is an unfinished document.

ILLUSTRATIVE EXAMPLERetention cap deployed 10-09; disk growth flat for 14 days. Runbook updated and reviewed in the 10-16 ops review. Alert thresholds live; paged once on a legitimate growth spike.

QUESTIONS

RCA, answered briefly.

What is an RCA template?

A structured document that walks an incident from symptom to confirmed cause. Standard sections: problem statement, timeline, 5 whys analysis, contributing factors, corrective actions, and follow-ups. It keeps the analysis evidence-based instead of a blame exercise.

What are the 5 whys?

A root-cause technique where you ask "why" repeatedly — typically five times — with each answer becoming the next question. It moves the analysis past surface symptoms ("the server crashed") to the underlying cause ("no alerting on disk growth").

How do I write a root cause analysis for an IT outage?

Start with a precise problem statement and a timestamped timeline. Apply the 5 whys to the timeline, separate contributing factors from the single root cause, record corrective actions with owners and dates, then validate that the fix worked.

What is the difference between RCA and a postmortem?

RCA is the analysis that identifies why an incident happened. A postmortem (or post-incident review) is the broader review document — timeline, impact, the RCA itself, and action items. Teams often combine them into one record.

Can I use this template offline?

Yes. The template is plain text you can copy into any document. If you document the investigation in SolveStack, it also works fully offline: data stays in your browser's IndexedDB with no account or cloud connection.
