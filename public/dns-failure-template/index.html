THE TEMPLATE

Five checks, all comparisons, no guessing.

The worked example below is illustrative — not a real incident. It shows how each section reads when filled in.

SECTION 01

Compare the resolvers

Query the failing name against your internal resolver and a public one. Different answers mean the record probably exists and one view of it is wrong; the same wrong answer everywhere points upstream — at the zone, the delegation, or the record itself.

ILLUSTRATIVE EXAMPLEThe failing name resolved correctly on a public resolver and returned NXDOMAIN internally. The record was fine; the internal view was broken. Not a real incident.
SECTION 02

Ask the authoritative server

Resolvers cache and forward; the authoritative nameserver is the source of truth. Query it directly for the exact record type. If the authoritative answer is right, your problem is caching or forwarding — not the record — and editing the record will only add TTL confusion.

ILLUSTRATIVE EXAMPLEThe authoritative server returned the correct A record with a 300-second TTL. The internal resolver had cached an NXDOMAIN from before the record was created. Not a real incident.
SECTION 03

TTL and the last change

Every DNS surprise has a change and a TTL attached. Find when the record or zone last changed and how long the old answer can legitimately survive in caches. Many 'DNS is down' incidents are a correct change still propagating on a long TTL nobody remembered setting.

ILLUSTRATIVE EXAMPLEA migration the previous evening raised no errors, but the old record's 24-hour TTL meant some resolvers served the dead address until midday. Not a real incident.
SECTION 04

Split-horizon and conditional forwarding

Enterprises run two truths: internal and external views of the same name. A conditional forwarder removed during cleanup, or a zone transferred to only one view, breaks internal resolution while the internet sees perfection — and every external test you run will pass.

ILLUSTRATIVE EXAMPLEA cleanup change removed the conditional forwarder for the zone on one internal resolver pair; the other pair still resolved. Forwarding restored and documented. Not a real incident.
SECTION 05

Capture answers, not impressions

DNS evidence is text: save the full resolver output — question, answer, TTL, and which server answered — for the failing name and a working comparison. 'It doesn't resolve' cannot be handed to a network team; two resolver outputs can.

ILLUSTRATIVE EXAMPLEEvidence attached: internal vs public vs authoritative outputs for the failing name, timestamps aligned. The network team confirmed the forwarder gap from the outputs alone. Not a real incident.

03

QUESTIONS

DNS failures, answered briefly.

What should I check first when DNS resolution fails?

Compare answers before changing anything: query the failing name on your internal resolver, a public resolver, and the authoritative nameserver. Where the answers diverge tells you whether the record, a cache, or a forwarding path is wrong — three different fixes that guessing routinely confuses.

How can I tell a resolver problem from a record problem?

If the authoritative nameserver returns the correct record but a resolver returns something else, the record is fine and the resolver's cache or forwarding is at fault. If the authoritative answer itself is wrong or missing, the fault is in the zone or its delegation.

How long should DNS changes take to propagate?

As long as the previous record's TTL says — caches may hold the old answer for the full TTL after a change. A 24-hour TTL set during a migration means a full day of mixed answers. Lower TTLs a day before planned changes, and treat 'not propagated yet' as a state to verify with the TTL, not a guess.
