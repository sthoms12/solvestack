FIELD GUIDE / CORRECTIVE ACTION

CAUSE → ACTION → A CHECK THAT IT WORKED

Corrective Action Plan Template

A corrective action plan template is the list of changes that follow a cause you are willing to stand behind. It is not the analysis. The analysis explains why the incident happened. The plan says what will change, which role owns it, when it is due, and what result will show that it worked. Copy the blank plan, or read the worked example. The cause itself belongs on the root cause analysis template.

01

THREE WORDS

A correction is not a corrective action.

Teams close the incident when service is restored and call that the action plan. Restoration is the correction. The corrective action is the change that removes the cause. The preventive action is that same class of change somewhere the failure has not happened yet. Write the type on every line so a finished correction cannot hide an open cause. ISO 9001:2008 required a preventive-action procedure of its own. ISO 9001:2015 removed that separate procedure. Prevention sits in how you plan for risk, and corrective action includes asking whether the same nonconformity could happen somewhere else. The fields on this page follow that shape. They are a practical record for an IT incident, not a certificate of conformity.

Three action types. Closing one row does not close the others.
Type What it changes Close it when
Correction This instance. Roll back, restore, reissue, block the bad path, or drain the queue. The immediate impact has stopped, and the plan says whether the temporary measure is still in place.
Corrective action The cause of this failure, so the same failure does not recur here. The effectiveness check has been recorded. Deployed is not the same as checked.
Preventive action The same cause in a place that has not failed yet. That other place has the control, and a named role has looked.

An owner is a role that can change the system. A crowd is not an owner, and a colleague's name is not a substitute for the role. An action with no due date is a wish. If you cannot schedule it, write that down instead of leaving the date blank.

02

THE TEMPLATE

Seven fields. Then a check.

FIELD 01

Identity

A plan ID, the source (an incident, an audit, a failed change, or another record), the date, the role that owns the plan, and a status. Someone reading this later should be able to find the analysis from this block alone.

ILLUSTRATIVE EXAMPLECAP-2026-044, from incident INC-2026-044 on 2026-10-08. Plan owner: platform lead. Status: closed. Not a real incident.
FIELD 02

Problem statement

What failed, where, when, with the timezone, and the extent. Use the measurements you have. Point at the incident report if there is one. Do not paste the whole timeline here. The incident report template is that timeline.

ILLUSTRATIVE EXAMPLECI jobs against the internal package registry returned HTTP 401 from 09:40 to 10:06 UTC. Merge builds in two product groups failed. No production runtime was affected. Not a real incident.
FIELD 03

Containment already done

The correction: what stopped the current impact, which role did it, when, whether it is still in place, and the evidence. A rollback that is still in production is a temporary control. Say so, or the next reader will treat it as the permanent fix.

ILLUSTRATIVE EXAMPLEPlatform on-call reissued the CI robot credential, revoked the expired one, and re-ran the failed jobs. Finished 10:06 UTC. The replacement credential is the one still in use. Auth log has no expired-token errors after that time. Not a real incident.
FIELD 04

Cause

Name the method, from the root cause analysis tools you actually used. State the cause as something the team can change, the evidence, and the contributing factors that are not the cause. If the cause is not confirmed, write "not confirmed" and do not invent a permanent fix. The chain and the timeline stay on the root cause analysis template.

ILLUSTRATIVE EXAMPLEMethod: 5 Whys. The migration checklist covered human accounts and omitted service credentials, so the robot credential expired with no renewal job. Contributing factor: the alert watched job failure, not upcoming expiry. Not a real incident.
FIELD 05

Actions

One line each: an ID, the type, the change, the owner role, the due date, the status, and the evidence that will show it is complete. The change should be a system, a procedure, or a control. "Be more careful" is not an action.

ILLUSTRATIVE EXAMPLECAP-2, corrective: add service credentials to the rotation checklist, and add a renewal job that runs 14 days before expiry and pages if it fails. Owner: identity engineering. Due: 2026-10-22. Evidence: the checklist diff, and a drill where a forced failure paged. Not a real incident.
FIELD 06

Effectiveness check

Name what will be observed, the review date, the role that reviews it, and the result that closes the plan. Observe the original effect, not only the deployment. An action marked done on "merged" stays open until this result is written down.

ILLUSTRATIVE EXAMPLEReview on 2026-11-06 by the platform lead. Close only if CI shows no 401 from an expired robot credential after 2026-10-08, and the renewal job succeeded in the drill. Both were true. Plan closed. Not a real incident.
FIELD 07

Considered and not done

Write down the actions you discussed and rejected, and why. Otherwise the next incident reopens them as if they were forgotten. A broader study you are not doing, including an FMEA of a whole process, belongs here when it is out of scope for this plan.

ILLUSTRATIVE EXAMPLEHuman passwords were not rotated that day, because they were not the cause. A full FMEA of credential rotation was not required to close this plan. Not a real incident.

CORRECTIVE ACTION PLAN — WORKED EXAMPLE
Not a real incident.
========================================
Plan ID: CAP-2026-044
Source: incident INC-2026-044, package registry HTTP 401, 2026-10-08
Plan owner (role): platform lead
Status: closed

1. PROBLEM STATEMENT
   CI jobs against the internal package registry returned HTTP 401.
   Window: 2026-10-08, 09:40–10:06 UTC (26 minutes).
   Extent: merge builds in two product groups failed. No production runtime was affected.
   Detection: the CI failure alert.
   Incident report: INC-2026-044

2. CONTAINMENT (CORRECTION ALREADY DONE)
   - Reissued the CI robot credential, revoked the expired credential, and re-ran the failed jobs.
     Role: platform on-call. When: 2026-10-08, finished 10:06 UTC.
     Still in place: the replacement credential is the one in use.
     Evidence: auth log has no expired-token errors after 10:06 UTC, and the re-run jobs passed.

3. CAUSE
   Method: 5 Whys, recorded on the root cause analysis template.
   Root cause: the registry migration checklist covered human accounts and omitted service credentials, so this robot credential had a fixed expiry and no renewal job.
   Evidence: auth log expired-token errors from 09:40 UTC; secret metadata showing expiry that morning; checklist in the infrastructure repo with no service-credential row.
   Contributing factor: the alert watched job failure, not upcoming credential expiry, so the first signal was failed builds. That delayed detection. It did not cause the expiry.
   Analysis: RCA for INC-2026-044

4. ACTIONS
   - [x] CAP-1 — correction — reissue and revoke the CI robot credential, then re-run the failed jobs — platform on-call — 2026-10-08 — done — auth log clean after 10:06 UTC and passing re-runs
   - [x] CAP-2 — corrective — add service credentials to the migration and rotation checklist, and add a renewal job that runs 14 days before expiry and pages if it fails — identity engineering — 2026-10-22 — done — checklist diff merged, and a drill where a forced job failure paged
   - [x] CAP-3 — preventive — inventory every other robot credential that expires with no renewal job, and name a role for each one that remains — identity engineering — 2026-11-05 — done — inventory list with a role on every remaining secret

5. EFFECTIVENESS CHECK
   What was observed: CI authentication failures caused by an expired robot credential, and whether the renewal job succeeded in a drill.
   Review date: 2026-11-06
   Reviewer (role): platform lead
   Result that closes the plan: no such CI 401 from 2026-10-08 through the review, and the renewal job succeeded in the drill.
   Result recorded: both were true on 2026-11-06. Plan closed.

6. CONSIDERED AND NOT DONE
   - Rotating every human password on 2026-10-08. Human passwords were not the cause.
   - A full FMEA of the credential-rotation process. The checklist and the renewal job address the cause this incident showed. A broader FMEA would be a later design review, not a condition for closing this plan.

04

QUESTIONS

Corrective actions, answered briefly.

What is a corrective action plan template?

A corrective action plan template is a form for the changes that follow a confirmed cause. Each action has a type, an owner, a due date, evidence that it was completed, and a check that it worked. The plan does not replace the analysis. It records what will change because of the analysis.

What is the difference between a correction and a corrective action?

A correction stops the current instance: roll back, restore, reissue a credential, or block the failing path. A corrective action changes the cause so the same failure does not recur. A preventive action puts that control where the same cause could occur and has not failed yet. Closing the correction does not close the corrective action.

What fields should a corrective action plan include?

Include a problem statement, the source of the problem, the containment already in place, the cause and the method that produced it, the action list, an effectiveness check, and a note of what you considered and did not do. Each action names a role as owner, a due date, a status, and the evidence that shows it is complete.

How is a corrective action plan different from a root cause analysis?

A root cause analysis explains why the incident happened and keeps the timeline and the evidence. A corrective action plan starts from that cause and assigns changes. If the cause is not confirmed yet, limit the plan to containment and to the work that will confirm the cause. Do not write a permanent fix for a cause you have not established. The root cause analysis template is the record of the analysis.

When is a corrective action actually done?

A corrective action is done when the agreed check has been recorded, not when the change is merely deployed. The check names what will be observed, the review date, the role that reviews it, and the result that counts as success. If that result is missing, leave the action open.

Can I use this corrective action plan offline?

Yes. Copy the plain-text plan into any document, or print this page. Nothing typed into this page is saved or sent anywhere. The SolveStack app linked from this page stores an investigation in your browser and can export Markdown, HTML, JSON, and ZIP. It has no account and no cloud service.
